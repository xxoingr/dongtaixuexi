Cheat Engine 基础操作

Cheat Engine (CE) 是最常用的游戏内存修改工具。核心功能：附加进程 → 搜索数值 → 筛选变化 → 锁定修改。

精确数值搜索

1. 打开 CE → 附加目标进程
2. 输入当前数值（如 HP=100）→ 首次搜索
3. 游戏中改变数值（掉血到 80）→ 再次搜索 80
4. 反复筛选直到只剩几个地址
5. 双击地址加入列表，修改数值验证

数据类型

类型字节范围典型用途
Byte10-255子弹数、命数
2 Bytes20-65535小数值
4 Bytes40-4.29B血量、金币（最常用）
Float4±3.4E38坐标、速度
8 Bytes8极大大型数值、Double

模糊搜索

不知道具体数值时用：未知初始值 → 增大/减小 → 反复筛选。适合搜索血条百分比、计时器等。

复习锚点

数值搜索找到的是“当前值所在地址”，不自动等于永久地址。先用数值变化缩小候选，再用实际修改确认它确实影响目标状态。

验证与证据

看到什么说明什么
数值变化后候选地址持续减少筛选条件正在排除无关内存
修改候选值后目标状态立即变化该地址与目标数据存在直接关系
重启后地址失效它很可能是动态分配地址，需要继续追踪指针链

常见误区与排查

候选太多时，不要盲目修改；先在目标中制造明确的增减变化。数值搜不到时，先怀疑数据类型、显示值与真实值不同，或数值被拆分/加密，而不是立刻认定工具失效。

关联与防御视角

本课为指针扫描建立入口。防御侧关心的不是“有人找到一个地址”，而是进程外部是否反复读取、写入或锁定敏感数据。

版本与资料

结论与目标程序版本、数据类型和内存布局相关。资料方向：Cheat Engine 官方教程；Microsoft Learn 的进程虚拟内存概念。

基础-2 — 指针扫描 — 基址与多级偏移

✅ 已完成   Cheat Engine 指针扫描

为什么需要指针扫描

重启游戏后，之前找到的地址会失效——因为数据在内存中的位置每次都在变（ASLR、动态分配）。但基址不变，只需要找到从基址到数据的指针链。

CE 指针扫描流程

1. 找到血量的动态地址
2. 右键 → 「找出是什么访问了这个地址」
3. 游戏中让血量变化，CE 捕获到访问指令
4. 查看汇编：mov eax, [rcx+0x58] → 偏移 = 0x58
5. 记录 rcx 的值，继续往上追
6. 最终找到：TestGame.exe+0x1F4D8 → +0x0 → +0x58 = 血量

多级指针结构

[TestGame.exe + 0x1F4D8]  ← 基址（不变）
       ↓
    [g_pPlayer]           ← 第 1 级指针
       ↓ +0x58
    [HP = 100]             ← 最终数据

静态指针 vs 动态指针

类型重启后怎么找
动态地址❌ 失效每次重新搜
静态指针（基址+偏移）✅ 永久有效指针扫描 + 人工验证

复习锚点

动态地址会变，能跨重启复现的是“模块基址 + 指针解引用 + 偏移”的关系。偏移不是地址本身，而是对象内部字段相对某个指针的距离。

验证与证据

检查合格现象
重启目标程序原动态地址改变，但同一条指针链仍能到达正确数据
查看访问指令能把类似 [rcx+offset] 拆成对象指针与字段偏移
更换一次游戏状态指针链读取的值随对象状态同步变化

常见误区与排查

不要把寄存器当前值当成永久基址；寄存器只是某次执行时的临时上下文。指针链重启失效时，先检查模块版本、对象生命周期和中间层是否选错。

关联与防御视角

本课把“数据地址”推进到“对象结构”。后续逆向看到 [rcx+0x58] 时，应自然想到它可能是对象字段访问。防御侧则更关注异常读写是否围绕稳定模块偏移和敏感对象展开。

版本与资料

ASLR 会改变模块加载基址，程序更新也可能改变偏移。资料方向：Microsoft Learn 的地址空间布局与 Windows 调试文档。

基础-3 — LoadLibrary DLL 注入 — 第一个注入器

✅ 已完成   Visual Studio 2026, C++

什么是 DLL 注入

把你自己写的 DLL 塞进目标进程的地址空间，让它在目标进程内部执行代码。注入后你的 DLL 就像游戏自己的一部分——可以直接读写游戏内存。

LoadLibrary 注入原理（最经典的注入方式）

1. OpenProcess — 打开目标进程
2. VirtualAllocEx — 在目标进程里分配内存
3. WriteProcessMemory — 把 DLL 路径字符串写进去
4. CreateRemoteThread — 让目标进程调用 LoadLibraryA(你的DLL路径)
5. Windows 加载器加载你的 DLL → DllMain 执行

注入器核心代码

HANDLE hProc = OpenProcess(PROCESS_ALL_ACCESS, FALSE, pid);
LPVOID pRemote = VirtualAllocEx(hProc, NULL, 4096,
    MEM_COMMIT | MEM_RESERVE, PAGE_READWRITE);
WriteProcessMemory(hProc, pRemote, dllPath,
    strlen(dllPath) + 1, NULL);
LPTHREAD_START_ROUTINE pLoadLibrary =
    (LPTHREAD_START_ROUTINE)GetProcAddress(
    GetModuleHandleA("kernel32.dll"), "LoadLibraryA");
CreateRemoteThread(hProc, NULL, 0, pLoadLibrary,
    pRemote, 0, NULL);

为什么注入后不需要 OpenProcess

注入后你的 DLL 跑在游戏进程内部，和游戏共享同一个虚拟地址空间。一个普通指针就能直接读写游戏的内存——不需要跨进程 API。

复习锚点

LoadLibrary 注入的核心不是“把 DLL 文件复制进去”，而是让目标进程里的 Windows Loader 正常加载该 DLL。成功后 DLL 与目标共享同一虚拟地址空间。

验证与证据

检查点应看到的证据
模块视图目标进程模块列表出现预期 DLL
线程与入口能关联到远程线程与系统加载流程

常见误区与排查

路径编码错误会导致加载失败，含中文路径优先使用宽字符版本。位数必须匹配：x64 目标配 x64 DLL；不要在 DllMain 内做长时间工作或依赖复杂初始化。

它是后续 Manual Map 的参照物：前者把 Loader 工作交给系统，后者自己承担。防御侧可关联跨进程句柄、写入 DLL 路径、远程线程和新增模块这条行为链。

进程地址空间

为什么 DLL 注入后无需 OpenProcess？ 注入后 DLL 跑在游戏进程内部，共享同一虚拟地址空间——一个普通指针就能直接读写。

复习锚点

常见误区与排查

什么是 Shellcode

一段裸字节码，没有 PE 加载器、没有 CRT、没有导入表。必须自己从 PEB 找到 kernel32，自己解析导出表，自己动态拿函数地址。位置无关代码 (PIC)，shellcode 被放到任意内存地址都能正确执行。

x64 PEB 走法

GS:[0x60]         → TEB → PEB
PEB + 0x18       → PEB_LDR_DATA
LDR + 0x20       → InMemoryOrderModuleList
[rax]            → 1st: exe (skip)
[rax]            → 2nd: ntdll (skip)
[rax]            → 3rd: kernel32  → InMemoryOrderLinks
[rax + 0x20]     → kernel32.dll base (Win10 x64)

Shellcode 执行流程

1. PEB walk → kernel32.dll base
2. Parse export table → find "GetProcAddress" by name
3. GetProcAddress(kernel32, "LoadLibraryA")
4. LoadLibraryA("user32.dll")
5. GetProcAddress(user32, "MessageBoxA")
6. MessageBoxA(NULL, "Hello from shellcode!", "Shellcode", MB_OK)

主动注入 vs 系统被动注入

Day 5（手动映射）和 Day 6（Shellcode）都是主动注入——你自己调 OpenProcess、VirtualAllocEx、CreateRemoteThread 把代码塞进目标进程。

Day 7 是系统被动注入——你只调用一个合法的 Win32 API 注册钩子，系统在目标进程取消息时自动把你的 DLL 拉进去。

SetWindowsHookEx 工作流程

1. HookSetter.exe 调用 SetWindowsHookExW(WH_GETMESSAGE, GetMsgProc, hDll, 0)
2. 系统记录：全局 WH_GETMESSAGE 钩子已注册
3. 任何 GUI 进程调用 GetMessage/PeekMessage 取消息时：
   → 系统自动加载 HookDll.dll
   → 系统调用 GetMsgProc(nCode, wParam, lParam)
   → 末尾必须调用 CallNextHookEx，传给下一个钩子

关键：不碰目标进程。没调 OpenProcess，没调 VirtualAllocEx，没调 CreateRemoteThread。全是系统自己的正常行为。

HookDll.dll：钩子回调 DLL，导出 GetMsgProc，包含共享段 (.SHARED)

HookSetter.exe：LoadLibrary → GetProcAddress → SetWindowsHookEx → 消息循环 → UnhookWindowsHookEx

APC = Asynchronous Procedure Call

往别人线程里排队塞一个函数调用。不创建新线程，复用已有线程执行代码。类比：CreateRemoteThread = 闯进去开一桌饭，QueueUserAPC = 留张便签等他闲下来自己看。

Loader 行为谁负责？Windows Loader，还是注入方自己处理导入、重定位、TLS 等细节
防御方能看到什么？模块、线程入口、可执行私有内存、上下文变化与跨进程行为链

稳定、痕迹与控制权

越借助系统的正规流程，系统替你维护的秩序越多，所以通常越稳定；代价是模块、路径、线程和 Loader 行为更容易被观察到。越是自己控制执行链，就越要自己承担这些秩序：模块装载、内存权限、调用栈、寄存器和恢复现场。它不等于完全绕过系统，而是系统只提供基础能力，不再替你保证高级流程正确。

借系统流程：系统 Loader / 消息回调 / APC 机制

自己控制流程：私有可执行内存 / 自行处理 PE / 改写已有线程上下文

稳定性来自系统维护秩序；风险来自自己接管秩序。

线程劫持的原理

线程劫持的本质是临时改写一个已有线程的下一条执行位置：保存原始 RIP/EIP 与必要现场 → 让线程短暂进入 payload → 恢复现场并回到原始 RIP/EIP。如果没有保存原始位置，payload 结束后线程不知道该回哪里，原执行流会被截断。

它容易崩，是因为线程暂停时可能正在持锁、依赖寄存器中的值、使用栈上的局部数据，或正处于 Loader、GUI、同步等敏感逻辑。新建线程像给任务单独开一张干净的桌子；线程劫持则是在别人正在工作的桌面上临时插手。

反作弊：从证据反推注入家族

防御方不必一开始就准确叫出攻击技术名。更实用的顺序是：先建立可信的模块与内存边界 → 发现异常行为链 → 将证据映射到可能的注入家族 → 再做针对性验证。

Day 10 — 注入检测视角

✅ 已完成

本课要解决什么

不要把 RWX 当作唯一注入规则。检测要把模块、内存区域、线程入口和行为历史组合成证据链，区分可疑现象与更可靠的执行证据。

30 秒核心结论

私有可执行内存本身只是线索；线程从其中启动才是强执行证据。没有 RWX 也不能证明安全，因为载荷可先写入 RW 内存，再改为 RX 后执行。

DEP / ASLR / CFG 各自限制什么

机制限制对象对注入或控制流攻击的意义
DEP数据页能否执行阻止把普通 RW 数据页直接当机器码运行；攻击者仍可能申请或改成可执行页。
ASLR模块加载地址的可预测性让硬编码函数地址、固定 gadget 或部分 ROP 链不可靠；运行时泄露或解析实际地址后仍可能绕过。
CFG间接调用/跳转的合法目标限制控制流跳到未允许的目标地址；它不负责检测所有注入，而是增加任意跳转的难度。

检测证据链

可疑私有内存出现
  -> 写入载荷（若能观测）
  -> RW 改为 RX/RWX（若能观测）
  -> 线程从该地址启动，或控制流进入该地址
  -> 结合进程句柄、模块和调用上下文定性
观察说明误区
RWX 内存可写后立即执行，值得关注JIT、调试器等正常组件也可能使用，不能单独定性。
MEM_PRIVATE + RX不属于普通已加载映像模块的可执行区域只能说明来源值得核查，尚不等于攻击。
线程起始地址落入该区域该私有内存实际承担了执行入口这是强信号，仍应结合进程用途和时间线排除误报。

反注入思路

典型远程线程链是：获取目标进程高危句柄 -> 写入内存 -> 修改执行权限 -> 创建或劫持线程。防守应优先控制前端的高权限句柄，遵循最小权限原则，并监控写内存、改保护属性和创建线程等组合行为。单独的只读进程内存权限常用于诊断或扫描，不能据此直接定性。

尚未实测：本课未运行实时进程枚举、内存权限监控或调试器验证，因此没有把推理结论写成特定进程的实测结果。

常见误区

“没看到 RWX 就安全”是错误结论。先写 RW、再改 RX 的载荷在最终快照中可能只留下 RX；检测应尽量结合权限变化历史和线程执行位置。

Day 11 — x64 汇编 + IAT Hook

✅ 已完成   最小实验：自己 Hook 自己进程的 MessageBoxA

本课要解决什么

写一个能真正生效的 IAT Hook，并且用调试器证明执行链：调用被拦截 → 先进 Hook 函数 → 再调回原函数。前提是先吃透 Windows x64 调用约定——参数怎么传、栈怎么摆。

30 秒核心结论

IAT 槽位是存函数地址的 8 字节格子；IAT Hook = 把目标函数槽位里的地址换成自己函数的地址。程序执行 call [IAT槽位] 时照着格子里的地址跳，于是跳进 Hook 函数。Hook 函数想恢复原行为，必须先保存原地址，再通过保存的指针调用原函数。

x64 调用约定（四条规则）

规则内容意义
1前 4 个整数/指针参数 → RCX、RDX、R8、R9参数不压栈，直接放寄存器
2浮点参数 → XMM0-XMM3（整数浮点各自独立编号）游戏坐标等 float 参数在 XMM 里
3调用任何函数前，RSP 必须 16 字节对齐API 内部用 SSE 指令，SSE 要求 16 对齐，不对齐一进 API 就崩
4调用方预留 32 字节影子空间（Shadow Space）被调函数存放 RCX/RDX/R8/R9 的临时区

崩在别人家，错在自己家：RSP 对齐是“调用那一刻”由调用方保证的；崩溃点常在 API 内部，原因却在调用方没对齐。

INT vs IAT（导入表两列）

装什么比喻
INT（OriginalFirstThunk）函数名字购物清单
IAT（FirstThunk）函数真实地址收货地址

INT 和 IAT 里的函数按同一顺序排列：在 INT 里找到目标函数名，记下标，到 IAT 同下标取槽位。

IAT Hook 执行链

1. 找到目标函数在 IAT 里的槽位（PE头 → 导入表 → 目标DLL → 按名字匹配）
2. 保存槽位原值（原函数真实地址）到全局变量
3. VirtualProtect 把槽位所在页改成可写
4. 把槽位里的地址替换成 Hook 函数地址，再恢复页属性
5. 程序再调用该函数 → call [IAT槽位] → 跳进 Hook 函数
6. Hook 函数干完自己的事 → 通过保存的原地址调用原函数

寄存器实测值对应参数

已验证 vs 推测

已验证：槽位替换后调用进入 Hook 函数（调用栈）；Hook 函数内寄存器保存调用方原参数（寄存器窗口）；调用原函数后弹窗正常出现但内容被改（功能保留）。推测（未单独实测）：RSP 16 对齐与影子空间缺失导致的崩溃现象，本课最小实验未主动制造。

常见误区

  • “Hook 是替代原函数” ❌ —— 是插队加活，默认要调回原函数，否则程序功能被破坏（该弹的窗不弹本身就是最大破绽）。
  • “附加进程 = 注入” ❌ —— 附加进程是调试器挂到已运行进程，注入是把代码塞进别的进程，两回事。
  • “IAT 槽位是函数名” ❌ —— 槽位存的是地址，名字在 INT 里。

防御视角

IAT Hook 不改代码，只改数据（IAT 页）。检测侧可校验导入表完整性：比较磁盘上的 IAT 原值与内存中的当前值，或检查 IAT 页是否被写保护篡改过（VirtualProtect 留下的权限变化痕迹）。它是静态替换，容易被完整性扫描发现，属于低隐蔽性 Hook。

Day 12 — Inline Hook

✅ 已完成   最小实验：x64 self-hook + x64dbg

复习入口

已确认：把 Target 开头换成一张跳转牌：执行路线改去 HookAdd，但 RCX/RDX 里的参数 3/5 不变；被覆盖的原指令先放进 trampoline，Hook 处理完再接着执行。

不要混淆：Inline Hook 不是固定写 5 个字节：E9 只需要 5 字节，但被覆盖的范围必须在完整指令边界结束；x64dbg 先停在 ntdll 或 mainCRTStartup 也只是启动过程，不算 Hook 命中。

下一步：Day 13 VTable Hook：把函数入口改跳转，和把对象的虚函数表槽位换地址进行对比。

本课要解决什么

Inline Hook 要解决的是：目标函数已经在程序里，怎样在它一进门时把执行路线引到自己的 Hook，同时保留原来的行为。大白话：不把整栋房子换掉，只在 Target 门口放一块指路牌，告诉 CPU 先去 HookAdd。

30 秒核心结论

Inline Hook = 改目标函数开头的机器码。本实验把 Target 开头的完整指令复制到 trampoline，再把 Target 开头改成 5 字节 E9 rel32 跳转，并用 NOP 补齐到 8 字节。Target 被调用时先跳到 HookAdd；Hook 处理完通过 trampoline 执行被覆盖的原指令，再跳回 Target+8。

前置知识

需要知道 x64 下整数参数前四个通常在 RCX、RDX、R8、R9；知道机器指令不是固定长度；知道函数入口的字节可以被调试器和程序读取。这里的最小实验是自钩取（self-hook），不涉及跨进程注入。

执行链

1. 读取 Target 开头的原始字节
2. 只选择完整指令，复制到附近的 trampoline
3. trampoline 执行原始字节，然后跳回 Target+8
4. 把 Target 开头改成 E9 rel32 + NOP
5. main 调用 Target(3, 5)
6. CPU 从 Target 开头跳到 HookAdd，RCX=3、RDX=5 保持不变
7. HookAddBody 打印命中，再调用 trampoline
8. trampoline 执行原逻辑并回到 Target+8，最后返回 18

本实验的关键字节

位置实测字节含义
Before8B C1 03 C2 FF C0 8B C84 条完整的 2 字节指令
PatchedE9 0B 00 00 00 90 90 905 字节相对跳转 + 3 个 NOP
Restored8B C1 03 C2 FF C0 8B C8恢复原始入口字节

这里选择 8 字节不是因为 Inline Hook 永远必须覆盖 8 字节，而是因为本实验的 Target 入口刚好能用 8 字节容纳完整指令，并且代码用一次 8 字节写入完成补丁。

调试与运行证据（已实测）

证据看到的结果说明
独立运行Before result=18；After result=18；Restored result=18Hook 改了路线，但没有破坏原功能
Hook 日志[HOOK] Target(3, 5) was redirected here.执行确实进入了 Hook
普通 x64dbg停在 HookAdd；用户实测 RCX=3、RDX=5目标入口和参数寄存器均得到调试器证据

实验环境：Windows x64；Visual Studio 2026/MSBuild；InlineHookLab；Debug/Release x64；目标文件 学习\Dll1\x64\Debug\Day12InlineHook.exe 和 学习\Dll1\x64\Release\Day12InlineHook.exe；x64dbg x64。动态地址随 ASLR 变化，不把某一次 RIP 当成固定地址。

已验证 vs 仅为推测

已验证：入口字节发生 E9 detour；Target(3,5) 进入 HookAdd；Hook 停点的 RCX/RDX 是 3/5；trampoline 让结果仍为 18；恢复字节后 Target 仍返回 18。

仅为推测或未单独压力测试：多线程同时执行 Target 时，单次 8 字节原子写入能降低读到半截补丁的风险，但本实验没有做并发压力测试，不能据此宣称完整线程安全。真实 Hook 还要审核正在执行的线程、指令缓存刷新和 trampoline 的可达距离。

失败实验与误区

  • 把 5 字节当成固定覆盖长度：E9 本身是 5 字节，但如果前一条指令 2 字节、下一条指令 4 字节，只覆盖前 5 字节就会把第二条指令切开；CPU 之后读到的字节会错位，可能异常、崩溃或跑出错误结果。
  • 把 ntdll 停点当成 Hook 命中：x64dbg 启动目标时可能先停在 Windows 的系统加载代码或 mainCRTStartup。截图没有显示自己的 HookAdd，就不能算实验命中；这次通过清理入口停点并使用明确的 HookAdd 停点解决。
  • 只跳进 Hook 不回原函数：如果 HookAdd 做完自己的事就返回，原来的加法逻辑可能完全不执行；trampoline 的作用就是把被覆盖的原代码接回来。

不要混淆

Inline Hook目标函数入口的机器码执行入口的 E9 跳到 detour

逆向与防御视角

分析者看到函数入口突然出现 E9、FF 25 或其他长跳转时，应先保存原始字节，确认跳转目标，再判断是否存在 trampoline。防御侧可以比较磁盘镜像和内存中的代码入口，检查 VirtualProtect 后的代码页权限变化、私有可执行 trampoline、指令缓存刷新和线程同步风险。Inline Hook 直接改代码，通常比只换 IAT 槽位更容易在代码完整性检查中留下痕迹。

Day 13 — VTable Hook

✅ 已完成

复习入口

已确认：把当前对象的 vptr 换到一张可写的 vtable 副本，再把副本的 slot 0 改成 HookAdd；虚调用先进入 HookAdd，HookAdd 用保存的原始 Add 完成原逻辑，最后恢复原 vptr。

不要混淆：保存原函数地址是为了让 HookAdd 还能调用原 Add；复制 vtable 是为了隔离对象。直接改公共 vtable 会影响所有共享它的对象，原表只读时写入还可能崩溃。

本课要解决什么

VTable Hook 要解决的是：不改函数入口机器码，只改某个 C++ 对象通过虚函数表找到函数的路线。大白话：对象手里有一张“函数地址表”，这次只给当前对象换一张副本，把 Add 对应的格子换成 HookAdd。

30 秒核心结论

VTable Hook = 替换对象的 vptr 指向的虚函数表槽位。对象的第一个指针通常是 vptr，它指向 vtable；本实验复制原表的两个槽位，把副本 slot 0 改成 HookAdd，再把当前对象的 vptr 换到副本。原始公共 vtable 不动，其他对象不跟着改变。

g_originalAdd 保存的是原来的 Add 函数地址，作用是让 HookAdd 还能执行原逻辑；复制 vtable 和改 vptr 的作用是只改变当前对象的虚调用路线。这是两件不同的事。

  • 把自带 __debugbreak() 当作教学断点：程序会在调试异常和下一条 int3 之间来回切换，反复按 F9 也不能稳定得到普通断点证据。修复方式是移除自带 INT3，改用 x64dbg 在符号 HookAdd 上设置普通 F2 断点。

本课要解决什么

Day 11-13 都是在“改路”：换 IAT 地址、改函数入口、换虚表槽位。Day 14 改成“站岗”：不改目标函数机器码，而是在当前进程的异常分发链上注册一个 VEH（Vectored Exception Handler，向量化异常处理器），观察它怎样先于局部 SEH（Structured Exception Handling，结构化异常处理）收到异常，并决定自己接管还是继续往下找。

30 秒核心结论

本实验的简化分发顺序是：调试器 first-chance -> 进程级 VEH -> 栈帧关联的 SEH -> 调试器 second-chance -> 未处理异常终止。E0421401 在 Day14VehHandler 返回 EXCEPTION_CONTINUE_EXECUTION，搜索停止，结果从 8 变成 108；E0421402 在 VEH 返回 EXCEPTION_CONTINUE_SEARCH，随后进入 SehFilter，由 __except 处理并得到 200。

实验模型与边界

这里的“VEH Hook”是可验证的最小教学模型：VehHookTarget 主动调用 RaiseException，VEH 通过进程内共享状态改写结果，然后让执行继续。代码没有修补目标函数入口，也没有把它包装成可直接套用到任意函数的通用 Hook；真实异常型 Hook 还可能修改 CONTEXT、配合页保护或硬件异常，本课没有覆盖这些路线。

执行链和前提

0. AddVectoredExceptionHandler(1, Day14VehHandler) 在当前进程注册 VEH

路径 A：E0421401
VehHookTarget(3,5) 保存原结果 8
  -> RaiseException(E0421401)
  -> 调试器 first-chance（有调试器时）
  -> Day14VehHandler 读到 E0421401
  -> 写入 hooked=108，返回 CONTINUE_EXECUTION
  -> RaiseException 后继续，VehHookTarget 返回 108

路径 B：E0421402
RunSehFallbackPath 的 __try 调用 SehFallbackTarget
  -> RaiseException(E0421402)
  -> Day14VehHandler 先记录 VEH declined，返回 CONTINUE_SEARCH

本课要解决什么

前面 Day 12 用 INT3（软件断点）让程序停住，但那个方式会改动程序自己的代码字节。Day 15 学第二种停住程序的方式：硬件断点（HWBP）——不改程序一个字，靠 CPU 芯片内部的 DR0-DR7 调试寄存器盯梢。核心结论一句话：软件断点是在路上挖坑（改字节），硬件断点是在 CPU 记事本上登记地址（改 DR 寄存器），两者都能让程序停下，但留下的痕迹完全不同。

DR0-DR7 分工（CPU 记事本）

寄存器角色实操看到的值
DR0-DR34 个"盯梢地址"格子（最多同时盯 4 个，芯片出厂就设计死）初始全 0；挂断点后 = 断点地址
DR6报警记录本：哪个断点刚响过（命中后才变）命中后 bit0=1（1 号断点响的）
DR7开关面板：每个断点的开关 + 类型（执行/读/写）+ 监视长度执行断点 0x1；写入断点 0xD0001
DR4/DR5不存在（架构只给了 4 页）-

DR4/DR5 不是被占了，是根本没有——所以 x64dbg 里硬件断点最多同时挂 4 个。正常程序从不往 DR0-DR3 写东西（永远全 0），这是反作弊检测硬件断点的依据。

执行断点 vs 写入断点（触发条件）

同一个地址，可以选"什么时候算命中"：

类型什么时候停典型用途
执行断点（bph 地址,x）CPU 执行到这条指令前和软件断点 F2 用途相同，但不改代码
写入断点（bph 地址,w）有人往这个地址写数据的那一刻抓"哪段代码在改血量"——CE 的 Find what writes 底层原理
读取断点（bph 地址,r）有人读这个地址时监控变量被读取

写入断点停下的瞬间，RIP 正指向正在写数据的那条指令——"凶手"被当场指认。软件断点做不到这件事（它只盯执行）。

反检测闭环（为什么又爱又恨）

软件断点会改代码，所以程序自查代码字节找 CC 就能发现调试器；硬件断点不改代码，找 CC 没用——但它留下另一个痕迹：DR 寄存器被登记。反作弊的办法是读 DR0-DR3，发现非零就断定有人挂了硬件断点（正常程序自己永远不会写）。两招配合：查 CC 防软件断点，读 DR 防硬件断点。断点命中瞬间 DR6 也会置位，是第二条狐狸尾巴。

常见误区与失败点（实测）

  • 误区：内存/反汇编窗口看不到 CC，以为软件断点没设上。x64dbg 会对断点改写的位置"还原显示"原始字节，窗口里永远显示 40 57……；判断断点是否生效要看行为：F9 一跑，程序停 + RIP 指向目标 = 生效。
  • 误区：函数之间的 CC CC CC 是断点改的。那是 MSVC Debug 构建出厂就填的 int3 对齐填充（0x10AE 之后一整片），与断点无关，32 位 Debug 程序同样有。
  • 误区：硬件断点没改字节是因为 x64。硬件断点在 32 位也从不改字节，它天生就不碰代码。
  • 坑：寄存器窗口（DR0-DR7）找不到了。视图被切到"源代码"了——点 视图 -> CPU 找回；或按 Ctrl+R。
  • 坑：每次打开程序地址都变（ASLR）。g_hp/GameTick 地址以本次运行黑窗口打印为准。
  • 环境事实：x64dbg headless 调试模式下 ntdll 有 C0000005 噪音（LoadLibraryW 线程访问违例，标准 Win32 调试 API 下程序完全正常），已定位为 headless 特有缺陷，不影响普通 x64dbg GUI 实操。

本课要解决什么

前面天天用 x64dbg 下断点，但从没问过：断点命中后，程序是怎么"停下来"的？Windows 在里面扮演什么角色？本课把这条链讲透。一句话核心结论：调试器是异常分发的第一顺位——进程发生任何异常，Windows 内核都先查有没有调试器，有就先交给它；调试器放行后，才轮到程序自己的 VEH/SEH；都没有，才弹窗终止。

执行链：从断点到调试器

  1. CPU 执行到软件断点（CC / INT3），举手报告 → 产生异常 EXCEPTION_BREAKPOINT（0x80000003）
  2. Windows 内核接到异常，先查这个进程的 DebugPort 是否非空
  3. 非空 = 有调试器 → 异常包装成调试事件，走 DebugPort 专线传给调试器（调试器用 WaitForDebugEvent 收信）
  4. 调试器暂停显示现场（first-chance），按 F9/Shift+F9 = 放行（ContinueDebugEvent）
  5. 放行后内核才问程序自己：有 VEH/SEH 就交给它；都没有 → WER 弹窗"已停止工作" + 进程终止

DebugPort：门禁卡槽（双向专线）

每个进程的内核对象里有一个 DebugPort 字段，平时是 NULL（卡槽空着）。调试器接管进程（启动时创建，或运行中 attach）的那一刻，内核把线插上；之后这个进程的所有调试事件（断点、异常、线程创建、DLL 加载）都走这条线，调试器也能反向发指令（放行、读写内存）——所以叫"端口"不叫"邮箱"。一个进程同时最多被一个调试器接管，没有"多根线"的概念。反调试查的就是：这个本该空着的卡槽，现在是不是被插上了（IsDebuggerPresent 的底层原理，Day 17 细讲）。

时刻DebugPort异常给谁
独立运行（无调试器）NULL（空）程序自己的 VEH/SEH
被调试（attach/启动创建）非空（0xFFFF...）调试器最先（first-chance），放行后才到 VEH/SEH

调试事件循环：调试器的心脏

调试器不是处理一次就下班，它转着一个循环：WaitForDebugEvent（蹲在信箱边等）→ 处理（界面显示停在哪）→ ContinueDebugEvent（放行）→ 再等。只要循环在转，调试器就一直"挂"在程序上；F8/F9 每走一步 = 等一个事件、处理、放行。注意：不只有断点产生事件——线程创建、DLL 加载也报事件，所以调试器能告诉你"哪个 DLL 加载了"。

本课要解决什么

程序怎么自己发现"有人在调试我"？本课讲三个最经典的检查点，并用 attach 前后对比实测：哪些触发、哪些不触发。一句话核心结论：PEB.BeingDebugged（及其 API 版 IsDebuggerPresent）在"被调试"时必变 1；堆上的调试标志（HeapForceFlags）只在"进程被调试器创建"时才打上——中途 attach 不会触发它，三个检查点各管一段。

PEB（Process Environment Block）是每个进程的"档案袋"，记录路径、命令行、DLL 列表等身份信息；BeingDebugged 是里面一栏字节，平时 0，被调试时内核改成 1。IsDebuggerPresent 就是把"翻档案看这一栏"封装成 API——但调用它会在导入表留下函数名，分析者一眼看出"这程序在查调试器"，所以高级反调试自己直接读 PEB 内存，不留痕迹。

  1. attach 那一刻：内核给 DebugPort 插线（Day 16），同时在 PEB 档案标记 BeingDebugged=1——两个检查点立即触发
  2. 堆上的调试标志（ForceFlags）是进程创建时由系统按"是否调试创建"打上的；attach 时进程早已出生，系统不补标记
  3. 所以三个检查点合起来能区分"出生就被调试"vs"中途被挂上"——反作弊往往三个一起查

Day 18 — 高级反调试

本课要解决什么

Day 17 的三个检查点都在 main 函数里"翻记录"，而记录（PEB 公告栏）可以被破解者撕掉。本课讲三种更隐蔽的查岗方式：RDTSC 掐秒表（量执行时间）、TLS 回调（抢在 main 之前查）、NtQueryInformationProcess（绕开传话员直接查内核深层的 DebugPort 专线）。一句话核心结论：标记可以伪装，时间没法伪装；浅层档案能撕，内核金库的登记簿撕不到——三种方式各靠一个"伪装不了"的点识破调试器。

三个检查点

检查点问谁 / 靠什么独立运行中途 attach怕什么
RDTSCCPU 硬件时钟（指令直读，无中间人）基线 55~210 万 cyclesattach 不停顿不暴涨断点/单步停顿必暴涨，无法伪装
TLS 回调PE 文件 .CRT$XLB 名单，加载器在 main 前点名回调先查（0/0）—名单可被改（Day 19）

为什么 RDTSC 骗不了：系统时间 API（GetTickCount 等）是"大厅墙上的挂钟"，有报时员（函数调用）可以拦；RDTSC 是 CPU 硬件指令，程序自己低头看手腕上的秒表，不经过任何函数，没有"回答者"可替换。为什么 DebugPort 撕不掉：传话员（IsDebuggerPresent）看的是用户态公告栏（PEB），破解者伸手能撕；NTQ 查的邮路登记簿在内核金库里，用户态的手伸不下去——而 attach 时系统会立刻建好邮路，所以中途挂上也亮，这一点和 Day 17 的堆标志（attach 不亮）正好相反。

执行链

  1. RDTSC：t0=读一次时钟 → 执行被测代码 → t1=再读一次 → 耗时=t1−t0。调试器只要在中间停下（断点/单步），耗时就从"微秒级"暴涨到"秒级"（几十亿 cycles），一次停顿就露馅
  2. TLS 回调：程序文件里登记一张"入场名单"（.CRT$XLB 段），系统加载器在 main 之前先点名，名单上的回调先跑——检测代码放进回调里，就抢在"调试者在入口点下断"之前先看了一遍
  3. NTQ → DebugPort：程序调 NtQueryInformationProcess(ProcessDebugPort=7) 问内核"我的调试邮路建了吗"——没建（0）= 没调试；建了（非 0）= 有调试器正在跟我通信

本课要解决什么

Day 18 说每种反调试检测都有死穴；本课把死穴变成行动：手动 Patch 三处逃跑出口、理解 ScyllaHide 的"改答案"思路、建立"打地鼠→先摸清全图再动手"的反反调试思维。一句话核心结论：Patch 改的是"检测结果的使用处"，不是检测本身——检测照跑，逃跑的腿被打断。

三个 Patch 点（Debug x64）

#位置(RVA)原始改后堵住什么
1GuardDebugPort+0x122575 09（jne short +9）90 90（nop）DebugPort 非空→逃跑分支，岔路填平
2GuardDebugPort+0x122E74 18（je 1248）EB 18（jmp 1248）检查值非 0→逃跑，强制走正常路径
3GuardRDTSC+0x129776 18（jbe 12B1）EB 18（jmp 12B1）RDTSC 超阈值→逃跑，强制走正常路径

两种改法有什么不同

nop（90 90）：检测照跑——1227 的 movzx eax,[rsp+28]（查 DebugPort）和 test eax,eax 都照样执行，只是"根据结果跳去逃跑"这个动作被抹掉。门卫还在查岗，但查完动不了。jmp（EB 18）：把"满足条件才跳"改成"无条件跳"，检测结果被强制无视，岔路口改成了直行道。共同点：动手术刀的位置都是检测结果的出口，不是检测本身——这正是手动 Patch 与 ScyllaHide 的差异：ScyllaHide 注入 DLL 后 Hook 掉检测函数（如 NtQueryInformationProcess），让"查岗的传话员"被收买、问什么都答"没有调试器"；手动 Patch 则是直接改被保护程序的指令字节。一个改答案，一个改程序。

反调试检测像打地鼠

救场前第一轮只堵了门卫 1 的 DebugPort 检查，门卫 2 的 RDTSC 接棒逃跑（RDTSC=40329279 超阈值）——检测是一点一点冒出来的，不是一次全亮。真实保护软件里检测分层 + 接力：查调试器、查断点、查补丁、查钩子、查内存改动……patch 一层冒下一层。所以反反调试的正确姿势不是"哪冒头打哪"，而是先摸清检测点全图，一次把所有逃跑出口堵上——今天三处一起核对、一起改，就是这个思路。

实操证据（2026-08-14）

三处 Patch 后按 F9：程序输出 "15 轮全部通过，没有逃跑" + done；每轮照查 DebugPort=0xFFFFFFFFFFFFFFFF、PEB=1（被调试的证据都在），但逃跑岔路全被堵死。断点列表里的 kernel32.FatalExit 断点当"逃跑警报器"：命中时调用栈为 exit→_wassert→FatalExit（CRT 正常收尾路径，没有任何 day19 模块帧），证明不是门卫逃跑触发——警报器抓到的不是小偷，是物业自己的巡检。

失败实验与坑（重要）

  • 空格汇编输入 nop 只写 1 字节，挤乱下一条指令：75 09（jne）是 2 字节，nop 是 1 字节；只写 1 个 90 会留下半个 09，把下一条 0F B6 44 24 28 挤乱。根因：CPU 按字节流读指令，不是一行一行读。解法：Ctrl+E 二进制编辑写满 2 字节（90 90），或勾选"保持大小"让工具自动补 NOP。
  • x64dbg 环境 C0000005@ntdll+0x1C286 噪音：attach 后 F9 即停在 ntdll 访问违例，Shift+F9 放行两次无效。经 Sol 救场确认不是程序/Patch 问题，是 x64dbg 的 TLS 回调自动断点与 GamePP 注入 GPP64.dll 的初始化交互；关闭用户/系统 TLS Callback 自动断点后噪音消失，程序正常运行。

分析者视角：Patch 的特征是内存字节与磁盘文件不一致，防御方可以做 CRC/自校验（读自己代码算指纹，被改就报警）反制；ScyllaHide 的特征是 DLL 注入 + 检测函数被 hook。防御者视角：检测要叠用（一个被堵另一个接棒）、要自校验（防 Patch）、要互相对答案（你改平了时间反而暴露动手脚）——这些正是 Day 20 软件保护综述的引子。

Day 20 — 软件保护综述

本课要解决什么

前面 19 天都在攻击者角度（找入口、下钩子、躲检测、打 Patch），本课第一次掉头看写程序的人怎么保护自己：加壳、混淆、自修改、反篡改、VM 保护五大招式各自在防什么、要付什么代价。一句话核心结论：保护不是让人破不了，而是让破起来不划算——五招可以叠加，每加一层就多扒一层皮。

五大招式对比表

招式大白话藏/挡什么主要代价攻击者的路
加壳（Packer）程序打成压缩包，双击边解边跑藏入口点（EP）和导入表（借 Windows 函数的清单）体积膨胀等解壳瞬间做内存转储（dump）
混淆（Obfuscation）把文章改成倒装句+缩写，意思不变搅乱代码顺序/等价替换（a+1 写成 a-(-1)）可读性变差难维护单步跟踪拼效果，费劲但能读懂
自修改（Self-modifying）程序自己给自己 patch文件里的代码和跑起来的对不上账容易改坏自己（字节数错就崩）软件断点（CC）会被冲掉，改用硬件断点（DR 寄存器，只盯地址不改字节）
反篡改（Tamper detection）程序自己查自己有没有被改防改代码、防换环境（调试器/模拟器）误报+代码变重不动检测，专打检测结果的出口（Day 19 打法）
VM 保护（Virtualization）把程序翻译成只有翻译机能懂的密文连"谁在执行"都换了：CPU 跑解释器，真逻辑在字节码里速度慢几十倍，只能重点保护关键段先逆向翻译机规则，极费功夫（VMP 是这种技术的产品名）

最容易混的三组区别

  • 加壳 vs 混淆：壳管"门面"（藏入口点和导入表，运行时整个解出来）；混淆管"内部"（改程序自己的代码长相）。
  • 混淆 vs VM 保护：混淆改的是代码长什么样（还是 CPU 直接跑的真指令，能读懂）；VM 改的是谁在跑（CPU 只跑翻译机，逻辑锁在字节码里，必须破译规则）。
  • 反篡改 vs 反调试：一家人——反调试是反篡改的特例（检测环境被换成调试器）。检测和对检测结果的反应是两段分开的，Day 19 只 patch 反应、检测照跑。

木桶原理与重点保护

攻击者不啃最硬的点，专打旁边没设防的地方。所以：没有总闸可掐（验证结果混进功能数据，改数据=程序拿错数字自己跑崩，找不到可 nop 的逃跑动作）；只保护关键段（全程序上 VM 保护会卡到没法用，只保授权验证/核心算法一小块）。目标永远是提高逆向成本：时间 > 收益，攻击者自然放弃。

Day 21 — 内核架构基础

✅ 已完成

本课要解决什么

前面 20 天都在用户态（Ring3）打转，本课第一次看清 Windows 的分层结构：程序住在哪、高危操作谁来做、跨层走哪扇门。一句话核心结论：用户态程序（Ring3）权限最低，任何碰硬件/碰别的进程的高危操作，都必须通过 syscall 这扇固定门递申请单，由内核（Ring0）代劳再返回结果。

两个圈子对比表

Ring3（用户态）Ring0（内核态）
谁住这你的 exe、游戏、浏览器Windows 核心、驱动
权限最低，处处受管最高，碰一切（内存/硬件/别的进程）
出错后果只崩自己一个整个系统蓝屏
类比小区住户物业总控室

系统调用（syscall）执行链

程序要读文件，文件在硬盘、硬盘只有内核能碰，程序不能自己伸手，只能打报告。完整链：

用户态程序调用 ReadFile（用户态窗口函数）
  → ReadFile 内部执行 syscall 指令（跨圈的门，机器码 0F 05）
  → CPU 身份 Ring3 切到 Ring0
  → 内核按服务号查 SSDT 找代码地址
  → 内核执行、返回结果、切回 Ring3

关键点：跨圈只有这一扇固定门，翻墙行不通——CPU 只认 syscall 这条正式通道，别处想直接碰内核会被当场拦下。这也是保护体系能成立的原因。

SSDT（系统服务描述符表）

内核提供很多服务（读文件/开进程/分配内存），每项对应一段代码。程序递单子不报人话、只报服务号（Service Number）；内核拿号去 SSDT 查“号 → 代码地址”。

SSDT 与导入表（IAT）是同一类东西：都是“查表找地址”。区别：IAT 在每个程序自己肚子里（改它只影响单程序，像改一家店门口路牌）；SSDT 在内核里、全系统共享（改它影响所有程序，像改全市地图）。改 SSDT 就是 SSDT Hook——与 Day 11/12 IAT/Inline Hook 同思路，只是换了张更高权限的表（Day 23 主角）。

失败实验与坑

  • 不带 --lab 程序结束太快，来不及 attach；要留窗口用 --lab（打印锚点后等 Enter）。

Day 22 — 内核回调机制

✅ 已完成

本课要解决什么

Day 21 看清了 syscall 这扇跨圈的门。本课第一次走到门的另一侧，认识两个新角色：驱动（.sys）和内核回调。核心问题：杀软、EDR 是怎么在某个程序刚被启动的第一时间就知道的？一句话核心结论：回调 = 先把"联系方式"登记给对方，事件发生时对方反过来调用你——方向与普通调用相反。杀软靠 PsSetCreateProcessNotifyRoutine 把回调登记给内核，于是每次有进程创建/退出，内核都会反过来叫它。

一条链：从报到到被叫

驱动被加载进内核圈
  → 内核调用 DriverEntry（报到窗口，只被调用这一次）
  → DriverEntry 里调用 PsSetCreateProcessNotifyRoutine，把回调函数地址交给内核（留电话）
  → 以后每有进程创建/退出，内核按地址反过来调用这个回调（被叫，方向相反）
  → 回调快速返回，内核才让进程继续跑
  → 卸载时 DriverUnload 注销回调（别留空号，否则蓝屏）

关键点：回调被叫的时候，进程创建才进行到一半、还没真正跑起来，所以回调不只能"看"、还能"拦"；也因此回调必须快速返回，否则全系统的进程创建都会被拖慢。

回调 vs 普通调用

普通调用回调（callback）
方向你主动去调别人别人在事件发生时反过来调你
类比你打电话叫外卖你留电话，快递到了快递员打给你
谁先动调用方被调用方先登记，事件驱动

Day 23 — SSDT Hook 原理

✅ 已完成

本课要解决什么

Day 21 认识了 SSDT 这张"服务号→代码地址"的表，Day 22 学会了回调。本课回答一个问题：如果有人把这张表里的地址偷偷改掉，会发生什么？一句话核心结论：SSDT Hook = 把内核"全市共享总电话簿"里某个服务号指向的地址，换成自己的地址；改的是表里的"地址箭头"，不是函数本身；因为表是全市共享的，所以一次改动影响全系统所有用该服务号的程序。

IAT vs SSDT（必须先分清）

IAT（导入表）SSDT
位置每个程序自己肚子里内核里，全系统共享
类比自家抄的小电话簿全市唯一总电话簿
改它影响只影响这一个程序影响全系统所有用该服务号的程序

SSDT Hook 三步：偷看 / 拦截 / 伪造

改表之后，所有打这个服务号的人都会先到你的函数。你的函数可以选择：照常转给真函数（偷看/监控）、直接掐掉（拦截）、假装自己是真函数回话（伪造）。

前提与门槛

SSDT 住在内核，想改它必须先在 Ring0。拿到 Ring0 的常见方式是加载驱动（或漏洞提权）——驱动是"进内核圈的门票"，不是作弊手法本身；SSDT Hook 是进内核后能用的"众多武器之一"。这也是为什么很多外挂要求"装驱动"：外挂装驱动=拿门票，进 Ring0 后才能读游戏内存、隐藏自己、做 SSDT Hook。

内核调试 KD / WinDbg

SSDT 在内核里，普通 Ring3 调试器（x64dbg）被权限墙挡住看不见。要看内核得用内核调试器（KD，即 Kernel Debugger），标准工具是 WinDbg，通常两台电脑连接（目标机 + 主机）。墙外的工具看不到墙内的表。

VTL0 / VTL1（比 Ring0 更高的隔离）

VTL（Virtual Trust Level）和 Ring 是两套不同的分层标准：Ring 管"这段代码能碰什么"，VTL 把整台电脑切成互相隔离的"虚拟房间"，每个房间里都能有自己的 Ring0/Ring3。正常系统和所有驱动跑在 VTL0；VTL1 是更安全的房间，放最敏感的东西（内核保护、防作弊核心、密钥）。VTL0 里即使拿到 Ring0，也看不到 VTL1 里的东西——不是权限不够，是你在错误的那栋楼里。所以现在"进 Ring0"不再等于"通关"。

Day 24 — 驱动通信 + 对象生命周期

✅ 已完成

本课要解决什么

Day 22 学了驱动入口，Day 23 学了改内核表。本课回答两个更实际的问题：用户态程序怎么和内核圈里的驱动"递话"？内核里的对象怎么知道"什么时候能安全销毁"？一句话核心结论：驱动通信 = 驱动开一个"接待窗口"，用户程序递"指令单"（控制码 + 输入/输出缓冲区）；对象生命周期靠"引用计数"记账，借了 +1、还了 -1、降到 0 才回收。

驱动通信（IOCTL）

用户态程序够不到内核圈的驱动，得走驱动主动开出来的通道。用户程序递一张指令单（IOCTL，即 I/O Control），单子上有三样：控制码（编号，告诉驱动办哪件事）、输入缓冲区（递进去的材料）、输出缓冲区（递回来的结果）。驱动一看控制码，就知道跑哪段代码。这跟 Day 21 服务号、Day 23 服务号 0x23 是同一套路：不报人话，只报编号，接收方查号办事。

共享内存

一次递一张单子适合偶尔说几句话；频繁传大量数据时，改让两边共用一块内存，直接读写，不用一次次递单子。关键理解：一块共享内存可以有多个不同的虚拟地址（视图），它们都映射到同一块底层内存——就像一栋房有两扇门、两个门牌，推门进去是同一间房。

有人归还-1像还书销账
降到 0回收没人用了，才销毁

两个反向错误都很致命：该减没减 → 内存泄漏（对象永远不回收，占内存）；减多了 → 蓝屏（对象被提前销毁，还有人用）。铁规矩：借了必须还，成对操作，配平。这与 Day 22"注册回调必须注销、别留空号"是同一个道理。

IRQL 与锁

内核是很多人同时干活的地方，需要两样东西维持秩序：锁管"谁先进、别人在外面等"（像公共厕所"有人/无人"），防止并发读写冲突导致系统崩溃；IRQL（Interrupt Request Level）管"谁的优先级更高、高优先级能不能停顿"。本课只建立概念，具体用法留后面实战。

失败实验与坑

  • writer 和 reader 地址不同是正常现象：不同虚拟地址可映射到同一块内存，判断共享成功看内容是否一致（match=true），不看地址是否相同。
  • 不要把 0x800 当成真实 IOCTL 编号：它只是本实验自定义的模拟控制码。
  • 不要把"内存泄漏"说成"数据泄露"：忘减引用计数导致的是对象不回收、占内存（内存泄漏），不是敏感数据外泄（数据泄露）。
  • reclaimed=true 是模拟回收标志：不是 Windows 对象管理器真实销毁对象的证据。
  • irql_lock=THEORY_ONLY 不代表模拟了 IRQL：这行是主动声明"没模拟"，避免误导。

逆向者：分析驱动功能，第一步先看它注册的设备对象和 IOCTL 控制码——控制码是用户态和驱动约定的"暗号"，逆向出控制码就能理解驱动暴露了哪些能力。防御者：驱动通信是外挂把用户态和内核态串起来的桥梁，反作弊会重点查"谁在给驱动发指令"；引用计数/锁用错是驱动蓝屏的头号原因，稳定驱动必须把"借还配平"做扎实。

Day 26 — 内核对象管理

✅ 已完成

本课要解决什么

内核基础阶段的收官一课。前面学了驱动、回调、改表、通信、过滤器，本课把这些收口到一个核心问题：内核怎么把"进程、线程"这些当作"对象"统一管理，又怎么保护它们不被别人乱碰？一句话核心结论：用户态程序访问内核对象拿到的永远是"句柄"（号码牌）而不是对象本身；ObRegisterCallbacks 就是卡在"打开进程/线程句柄"这道门前的检查站，在别人拿到句柄之前就把它挡住。

内核对象与句柄

内核对象 = 内核统一管理的"东西"的统称：进程、线程、文件、注册表项、事件都是；你程序里的普通局部变量不是。用户态够不到内核，所以内核不给程序对象真身，而是发一个句柄（Handle）——一个"号码牌"，程序凭号访问。同一个对象，不同程序拿到各自不同的句柄。

ObRegisterCallbacks：又一个检查站

Ob=Object（对象），RegisterCallbacks=注册回调。驱动调用它，就是告诉内核："以后每当有进程/线程的句柄要被打开、复制、使用时，先叫我。"于是谁想打开某进程，第一步先要"拿句柄"，就在这一步被回调检测。

进程保护的本质

游戏反作弊、杀软"保护自己进程"的核心思路：在句柄这道门提前设卡。外挂想读游戏内存，第一步必须先"打开游戏进程的句柄"；ObRegisterCallbacks 在这第一步就拦住，让外挂连句柄都拿不到（或拿到降权句柄），就更别提读内存、改数据了。保护在前、不是补救在后。

  • 本实验不是真实 ObRegisterCallbacks：没由驱动注册、没过滤真实内核句柄。

逆向者/防御视角

防御者：ObRegisterCallbacks 是"进程保护/句柄保护"的底层武器，游戏反作弊和杀软都用它在句柄层挡住外挂与恶意软件的探测、注入、读写。逆向者：分析保护类驱动时，重点看它有没有注册 ObRegisterCallbacks、回调里对"哪些进程+哪些访问权限"做了拦截——这决定了保护的范围和强度。攻击者视角：绕句柄保护是内核攻防的难点，常需更底层的技巧，这也推动了后续更高级保护（如 VTL1）的出现。

✅ 已完成

本课要解决什么

内核基础阶段结束，进入综合实战。第一个实战问题：游戏的内存不是一堆乱码，里面有规律——怎么从"只知道一堆地址"里认出 vector、string 和对象结构？一句话核心结论：搞清游戏引擎 = 拿到"内存对象怎么摆"的规律地图；STL 容器有固定长相（vector=3 个指针、string 短串就地长串外存），学会认这些长相，就能从地址堆里认出有意义的东西。

游戏引擎 = 内存地图

游戏大多架在引擎（Unity / Unreal Engine）上，引擎决定内存布局。同一个引擎做的游戏，对象排布规律高度一致——摸清一套，就能套用到同类游戏。搞清引擎的核心收获是"内存怎么摆"的规律，不是它用什么编程语言。

vector 长相：3 个指针

vector（动态数组）自己是个 24 字节的"壳"，里面装 3 个指针：begin（第一个元素）、end（已用区间的末尾边界）、capacity（租来的整段空间的末尾）。真正的一列元素租在外面。

begin ────────── 已用元素 ────────── end ─── 备用空格 ─── capacity
        (有效数据)                          (租了还没用)

认 vector 的铁证：end - begin = 元素个数 × 每个元素大小；capacity - begin 对应预留槽数。end 指向"最后一个元素的下一格"，不是最后一个元素本身。

string 长相：SSO

string 是 vector 的近亲，但有 SSO（Small String Optimization）：短字符串就地存在对象自己身上，长字符串才外存、对象身上留指针。所以逆向认 string 要分两种：短串的字符紧挨对象（`storage=INLINE_SSO`），长串是指针指向外部堆（`storage=EXTERNAL_HEAP`）。

对象结构恢复

一个对象 = 一组字段按固定偏移排布。认对象就是认"字段名 → 偏移 → 值"：例如 PlayerRecord 里 id 在偏移 0、health 在偏移 4、score 在偏移 8、team 在偏移 16。字段地址 = 对象基址 + 偏移。

  • 所有地址每次运行都变（ASLR）：只能比顺序、差值、归属关系，不比绝对地址。
  • end 不是最后一个元素：是"最后一个元素的后面"，capacity 是"全部预留空间的后面"。
  • vector 的 24 字节三指针是当前 MSVC x64 实现：不是所有编译器的永久保证；项目故意固定 _ITERATOR_DEBUG_LEVEL=0，否则 MSVC Debug STL 会加调试字段、不再是三个连续指针。
  • string 的 SSO 阈值（15）随编译器/版本变：不能硬记"15"。
  • 短串对象开头是字符、不是指针：不能把对象开头字节误读成外部指针；只有长串才能把对象起始的第一个机器字解释为字符缓冲区指针。
  • 对象尾部可能有对齐填充：PlayerRecord 最后字段在偏移 16，但对象总大小 24。

逆向者/防御视角

逆向者：游戏逆向的第一步常是"认引擎 + 认容器"——先定引擎，再用 vector 三指针、string SSO、对象偏移这些规律去读内存，把原始字节翻译成"一列敌人""玩家名字""某对象的血量"。防御者：知道攻击者会按这些规律自动扫描内存找关键对象，反作弊会做内存加密、对象分散、假数据等对抗，让"认长相"不再直接命中。

Day 28 — 游戏数据分析

本课要解决什么

Day 27 学会了在"运行中的内存"里认 vector/string/对象。本课换个战场：逆向不只在内存里，也在"躺着的文件"里——存档、网络包、资源、程序本体都是能分析的对象。一句话核心结论：分析二进制 = 按"字段偏移、大小、字节序"这些格式规则，把一堆原始字节翻译成人话。

四个分析对象

对象是什么怎么分析

静态 vs 动态（互补）

静态分析（IDA/Ghidra）：不运行程序，直接读文件，反汇编/反编译机器码——快、安全，能摸出框架。但网络包、运行时才解密的数据、内存临时值这些"运行才出现"的东西，静态看不到，要靠动态分析（运行、下断点、抓包）。两者互补，不是二选一。

小端序（Little Endian）

多字节整数在内存/文件里怎么存的问题。小端序 = 低位字节放前面（低地址）、高位字节放后面，读的时候倒过来拼。例：gold 存成 40 E2 01 00，倒过来拼成 00 01 E2 40 = 0x0001E240 = 123456。注意"40 是低位放最前"，不是"00 放低位"。

实操证据链（2026-08-23）

Day28BinaryDataAnalysisLab（自建字节，不碰真实游戏/网络/IDA）演示两段二进制解析：(1) 存档 16 字节小端序，magic=SAVE/version=1/level=27/gold 偏移 8 占 4 字节 raw=40 E2 01 00 → value=123456/equipment_count=3/checksum=625 校验通过；(2) 协议包 9 字节，opcode=0x1001/payload_length=5/player_id=42/action=7。--tampered-save 把 gold 首字节 0x40→0x41，checksum 重算不匹配，CHECKSUM_MISMATCH 拒绝（退出码 3）。后台 day28_check.py 输出 PASS。

失败实验与坑

  • 小端序不能从左到右直接读：40 E2 01 00 要倒着拼才是 123456。
  • offset 是字段相对整段数据起点的位置：不要和 end/偏移混用。
  • checksum 只是演示"格式校验"：不是现实游戏的通用算法。
  • 本工程不构成真实游戏分析证据：没碰真实存档/流量/解包，没装 IDA/Ghidra。
  • --lab 会等 Enter 是教学停留点：不是卡死。

逆向者/防御视角

Day 29 — 反外挂分析

✅ 已完成

本课要解决什么

前面学会了注入、Hook、反调试、内核、逆向、数据分析，本课站到"防御方"视角，回答一个问题：反外挂（Anti-Cheat）是怎么发现和拦截外挂的？一句话核心结论：反外挂是分层设防——特征码认长相、行为检测认动作、服务器侧校验藏数据，多层互补、层层叠加，提高攻击者的绕过成本。

分层设防

任何单层检测都可能被绕过，所以反外挂不赌单点。关键在互补：特征码堵"已知长相"、行为检测堵"可疑动作"、服务器校验堵"本地改数据"。攻击者过得了这层、过不了下层，成本越来越高。

三个层次对比

特征码行为检测服务器侧校验
看什么外观（字节/字符串匹配）动作（读内存/注入/调试）数据在谁手里
能抓已知外挂新型/易容外挂本地改数据攻击
怕什么加壳/改特征误伤正常程序服务端自己也有漏洞
类比看脸抓人看动作抓人账本锁在大老板手里

威胁建模

方法论：防御前先换位思考，系统列出"攻击路径 → 薄弱点 → 防御措施"，再有的放矢地设防。攻击路径就是前面所有课讲的：读内存、改内存、注入、Hook、改存档、伪造协议、加载驱动、SSDT Hook……反外挂针对这些路一条条堵。

实操证据链（2026-08-24）

失败实验与坑

  • 射击命中≠反外挂证据：命中反馈只是靶场体验，正式证据是终端的三层扫描结果。
  • 必须靠近终端再按 E：距离不足不会开始扫描。
  • Esc 只打开暂停菜单不直接退出：退出需确认。
  • 单层可被绕：加壳绕过特征码、改动作绕过行为检测；所以必须多层互补。
  • 层数多≠一定强：堆同类检测无效，要互补的层。

逆向者/防御视角

防御者：反外挂是"分层设防 + 威胁建模"，先想清攻击路径再针对性设防，关键数据放服务器。逆向者：分析一个反外挂，就是反着拆它的层——先看它认什么特征码、再看它监测哪些行为、最后看哪些数据在服务器。攻防双方都在抢"层"的制高点。

本课要解决什么

前 29 天学到的 PE、注入、Hook、反调试、软件保护、内核机制、游戏数据分析和反外挂，并不是互不相关的招式。Day 30 要把它们串成一条完整链：先看懂程序怎样组织和装载 → 理解代码怎样进入目标上下文执行 → 怎样接管既有执行路径 → 双方会留下和寻找哪些痕迹 → 程序怎样提高分析与篡改成本 → 最后站在攻防两侧评估整套防线还缺哪一层。

一句话核心结论

PE 解释程序如何组织和装载；注入解决代码如何进入目标上下文执行；Hook 解决执行流如何被接管；检测与反调试寻找分析和干预留下的痕迹；保护提高理解、修改和稳定绕过的成本；反外挂则依据威胁模型，把客户端、内核与服务器证据组合成相互补位的多层防线。任何单层都可能被绕过，可靠防御来自可验证、可关联、能够互相补位的整体设计——这就是"以攻促防"。

三处关键纠偏（比入门比喻更准）

  • Hook 不是"改箭头不改函数"：那是入门比喻。准确说法是 Hook 改变后续执行路径，实现时可能改地址表（IAT/VTable），也可能直接改函数入口字节（Inline Hook）。
  • 保护不能保证"找不到、看不懂、改不动"：真实目标是提高理解、修改和稳定绕过的成本，不是绝对防住。
  • Day 10/14/15/19/27/28 也接进总链：DEP/ASLR/CFG 是执行约束；VEH/HWBP 是观察执行流的入口；Day 19 是攻防往返（Patch 出口/打地鼠）；Day 27-28 把通用逆向接到游戏目标（对象结构 + 数据格式）。

完整攻防链

分析者先通过 PE 理解文件与内存布局、依赖关系和可定位入口；再选载荷、进入方式和执行入口取得目标上下文中的执行；随后通过 Hook 接管要观察或修改的调用路径。目标程序则从模块、内存、线程、异常、时间和行为中找干预痕迹；攻击方尝试藏痕迹、Patch 判断或绕开反应出口；防御方再通过加壳、混淆、反篡改、自修改和 VM 保护提高分析成本。进入游戏场景后，还要恢复对象结构和数据格式，区分客户端状态与服务器权威状态，最后按威胁模型评估各层覆盖、绕过路径、误报风险与补位关系。

三个视角的收官结论

安全研究员：结论必须区分"已实测 / 课堂推理 / 仍需验证"，单条痕迹不能推出最终结论。攻击方：真正重要的是分析每一步的前提、执行入口、Loader 责任、可见痕迹、失败位置和恢复路径。防御方：客户端、内核、服务器各有盲区，可靠防御靠多层证据关联、相互验证和补位，最关键状态由更可信的一侧决定。
